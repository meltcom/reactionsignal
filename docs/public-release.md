# Public release operations

## Status and release gates

This change provides account restrictions, audit history, assignments, shared aggregate caching, reduced polling, and an operations panel. It does not establish a supported production user count. The local benchmark excludes remote authentication, D1 scheduling, network and hosting quotas. Keep broad promotion on hold until the provider and staging checks below pass.

1. In Supabase, verify custom SMTP with a real delivered sign-in email to a non-team address; check rate limits, sender authentication, bounce handling, redirect URLs, and Google sign-in using a separate member account. Built-in email delivery is unsuitable for public membership. Record the tested account type and outcome, without tokens or passwords.
2. Verify Cloudflare billing plan, Workers daily requests/CPU limits, D1 storage/read/write limits and usage. Verify Supabase MAU, auth rate limits, database size and spend controls. Set provider usage notifications before promotion. Upgrade only after reviewing costs and measured use.
3. Deploy this branch to the isolated preview D1 using the existing branch preview build. Confirm migration 0039 succeeds, all member/moderator paths work, and production D1 remains untouched. Preview has discovery search disabled and a member allowlist; add designated test account emails to the preview allowlist for the test, retaining production settings.
4. Set RELEASE_STAGING_URL to an isolated preview hostname containing preview, staging or public-release; set RELEASE_STAGING_TOKENS to a JSON array of access tokens from distinct test accounts through a secure environment. Run `node scripts/staging-load.mjs`. It runs 200 authenticated reads, concurrency 20, without posting content. Do not paste tokens into logs. Target no errors and p95 under 1 second, then test realistic chat/contribution bursts with dedicated test data and inspect provider CPU, D1 rows read/written and Auth requests. Increase planned launch batches only after measurements remain within limits. The included read test alone does not certify write capacity.
5. Export production D1 before deploying; restore that export to a separate recovery database. Compare critical table counts, sample records and foreign key/integrity checks; validate authentication and member/moderator behavior against a recovery Worker. Record recovery duration and snapshot age. Confirm Cloudflare Time Travel retention for the actual plan. Never restore over production for a drill. Store exports encrypted with restricted access and a documented retention/deletion policy; they contain member data. Use Cloudflare's current D1 export/import and Time Travel documentation and verified database IDs. Existing preview is shared: use a separate recovery database to avoid overwriting it.
6. Configure operational alerts and test actual delivery; verify native provider alerts for outages that prevent the Worker/cron/D1 from running. Name the on-call owner, backup contact and escalation route. Review pending abuse/support at least daily during launch. With one moderator, plan limited launch windows and an emergency pause procedure until backup coverage is assigned.
7. After migration/deployment, smoke test a member and moderator session on the live site, including restriction/restore of a test member, review permissions, ETags, and status panel. Monitor the first limited cohort before broad promotion.

## Moderator accounts

Each moderator uses their own verified Supabase account. Add approved email addresses to `COMMUNITY_MODERATOR_EMAILS` as a comma-separated list in the appropriate Cloudflare environment; deploy the configuration. Never share a login. The current production configuration remains `meltcom@gmail.com` only. A moderator must sign in and create/load their profile before appearing in assignment choices. Removing an email revokes moderator privileges on the next verification; staff API requests are always reverified remotely.

Open Moderator Queue, then **Operations, staff assignments & audit**. The panel lists configured staff who have signed in, open cases, ownership filters, recent audit records and operational warnings. It distinguishes actors by stable account ID and displays known staff email addresses. All current moderators have the same privileges; separate administrator/support roles are a future extension.

Member management supports one-hour, one-day, seven-day or thirty-day suspensions; permanent bans; and restoration, with a required reason. Restrictions apply across protected requests immediately, independently of the brief identity cache. Staff accounts cannot be banned or suspended using this tool. Posting mutes remain separate. Appeal handling is manual through the existing support address; banned accounts cannot open protected support tools.

Audit records preserve actor ID, timestamp, reason and before/after evidence for new account restrictions, assignments, user changes, abuse moderation, mutes and content deletion. Existing catalog/contribution review trails remain in their original tables. The panel is not a complete consolidated audit of every historical administrative action. Establish retention for audit evidence and keep access moderator-only.

## Alerts and monitoring

Store `OPERATIONS_ALERT_WEBHOOK` as a Cloudflare secret in the desired environment, pointing to a chosen HTTPS monitoring receiver. No destination is configured by this change. Payloads contain service, warning code and timestamp, without emails, message bodies or tokens. Delivery has a five-second timeout, rejects redirects, records failure and throttles each warning to once an hour. A generic JSON receiver is needed; email or Slack delivery requires an adapter configured by the owner. Trigger and resolve a test warning and verify the chosen receiver before relying on it.

Current checks: five or more recorded server errors in 15 minutes, scheduled invocation older than one hour, and pending contribution/abuse/support cases older than 24 hours. The panel reports D1 page allocation, not provider billing usage or remaining quota. Errors are retained seven days with bounded cleanup. Structured request logs record request ID, path, status and duration; do not log authorization, URL queries or request bodies. Provider dashboards should alert on 5xx rates, elevated p95 latency, CPU failures, D1 throttling/storage, auth/email failures and approaching quota. The in-app checker cannot report a total Worker/cron/database outage; native monitoring is essential.

Ordinary verified member reads can reuse identity for at most 30 seconds, shortened to token expiry; writes, account verification and moderator access always call Supabase. Remote logout/revocation may take up to that interval for ordinary reads. Local suspensions/bans are checked every protected request. Temporary Auth failures return 503 and preserve the client session for retry.

## Recovery and rollout

Run `npm test`, `node scripts/release-check.mjs` and the authenticated staging test before rollout. The local recovery drill restores fixture data to an isolated temporary SQLite database and compares all rows and integrity; it does not test a real production D1 export or provider recovery.

Deploy migration 0039 before the new Worker. Migrations are additive. For a code regression, roll back the Worker version while retaining the new tables/triggers; do not delete audit or restriction data. An old Worker does not enforce the new bans, so a rollback requires a temporary member allowlist or maintenance access restriction until enforcement is restored. For a data incident, preserve evidence and the latest snapshot, validate recovery separately, then make an explicit recovery plan before modifying production.

For an incident: stop promotion; restrict new access using the existing member allowlist if necessary; preserve logs/request IDs; investigate Auth, Worker and D1 metrics; contact the assigned owner; restore service; then record cause, action and prevention. A single moderator is a staffing constraint even when the platform has spare capacity.

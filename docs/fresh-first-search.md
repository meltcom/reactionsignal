# Fresh-first keyword scheduling

Scheduled performer searches use three current first-page opportunities followed by one catch-up opportunity. Both lanes share the existing Pacific daily attempt cap (40 in production), 36-minute due interval at that cap, retry accounting, API/run budgets and 15-minute cron. Normally this provides about 24 current first pages and eight catch-up pages/day, rather than 32 current searches; capacity and retries can reduce those numbers. Neither lane guarantees provider indexing or discovery latency.

Fresh first pages supplement the full-window scan. They have independent progress/completion and query-rotation state. A successful first page completes only the fresh task, even when YouTube has more pages. It never advances the full-scan watermark or overwrites its token. A failed fresh page retains its original fixed query/window for retry. The catch-up lane continues the original `search-progress:*` cursor, including legacy tokens/unknown depths, and exhausts its fixed window before advancing `search:*`. When none exists, it starts the next full window using the existing overlapping lookback and weighted query rotation. There is only one outstanding full-window cursor per performer; supplemental first pages do not create an unbounded queue of overlapping windows. An experimental fresh song term is not promised its own exhaustive scan if song hints later change.

Fresh and catch-up use independent 12-name/6-reaction/2-experiment query-window rotations. Existing continuation rotation is preserved. Manual Find reactions retains the previous full-window continuation behavior and uses the same cap and touch/pacing state. Disabled search and exhausted quotas retain both cursors. An attempted lane advances the 3:1 turn before network work, so repeated catch-up failures cannot monopolize all future opportunities. A deferred run, disabled search or an already exhausted cap does not advance the turn. A crash between recording the turn and sending a request can skip an opportunity; it does not erase either saved cursor or refund quota.

The new strategy is `fresh-v3-first-pages-separate-catchup`. Page settings retain `lane: fresh|catchup`, allocation and unchanged cap/overlap/rotation for attribution. Historical page/result records are not rewritten. Health samples retain scheduler version/settings. No migration is needed: the change uses namespaced state keys and existing JSON settings fields. Rollback ignores fresh state and resumes the original preserved catch-up cursor; previously discovered IDs remain deduplicated and decisions are unchanged.

No changes to RSS endpoints, candidate recognition/approval, Shorts intake, known-channel upload scanning, history/backfill campaigns, quota configuration or migrations are included. Backfill's general-quota broker and reserve remain intact.

Validation covers current first pages while legacy continuations wait, unchanged fixed continuation bounds/depth, shared pacing/caps, failure retention and lane fairness, and watermark advancement only on catch-up completion. Provider-free tests establish scheduler behavior, not better live recall. After release inspect page settings/lane, current first-page age, catch-up progress, attempt counts, qualifying yield/new reactors, daily channel coverage and discovery delay. Compare measured periods with sample counts; do not claim a speed improvement from the first invocation.
